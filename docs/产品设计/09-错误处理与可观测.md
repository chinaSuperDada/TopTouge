# 模块 09 · 错误处理与可观测

> 覆盖：用户侧错误提示、技术错误上报、`client_errors` 表。
> 对应后端：`clientErrors.router` → `clientErrorRepo`。

---

## 1. 核心原则

**技术细节永远不给用户看。**

用户看到「无法连接服务器（errMsg: xxx）」只会觉得产品不专业，而且他既看不懂也做不了什么。

| 谁看 | 看什么 | 在哪 |
|---|---|---|
| 用户 | 一句白话（「网络开小差了，请稍后再试」） | `wx.showToast` / 页面错误态 |
| 管理员 | 完整细节：URL、错误码、errMsg、页面、机型、版本 | `client_errors` 表 |

---

## 2. 用户侧

- 所有失败提示均为**一句人话**（见模块 01 §6 文案规范）。
- 展示文案与错误对象解耦：`err.message` 是能直接展示的白话，技术细节放在 `err.detail`，**只用于上报**。
- 网络抖动自动重试（2 次），重试途中提示「网络较慢，正在重试…」，避免用户以为卡死。

---

## 3. 上报链路（`utils/errorReporter.js`）

```
出错
 ├─ 前端 reporter.report({ code, message, detail, url, method, statusCode })
 │    · 自动附当前页面路径、机型、品牌、系统、SDK 版本、运行版本
 │    · 静默 POST /api/client-errors
 ├─ 成功 → 从本地队列移除
 └─ 失败 → 留在本地队列（≤20 条，存 Storage），下次补发
```

- **上报绝不抛错、不阻塞主流程**——它是旁路。
- **云端模式**下没有可直接使用的绝对地址，由 `request.js` 在请求时借已建立的通道捎带（`flushWith`），避免循环依赖。
- 同时打一份到控制台，方便开发者工具里调试。

---

## 4. 后端接收（`POST /api/client-errors`）

- 接受单条对象或数组（客户端断网时会攒一批）。
- 全字段**长度截断**（不让客户端决定写多大）；单次批量上限 20 条。
- **永远返回 200**——上报失败不该再触发一次上报，形成循环。写不进去只打服务端日志。

---

## 5. 管理员查错

```sql
SELECT created_at, code, message, page, url, model, system
  FROM client_errors ORDER BY id DESC LIMIT 50;
```

---

## 6. 编码约定

> 改代码时注意：`.catch(err => showToast(err.message))` 这种写法要改成
> **展示固定白话 + `reporter.report({ detail: err.detail })`**。

---

## 7. 依赖与约束

- 依赖：模块 01（文案规范）。
- 被依赖：全部模块（每个模块的失败路径都走这里）。
- 约束：任何用户可见字符串不得包含 errMsg / 状态码 / 错误码 / URL / 堆栈。
