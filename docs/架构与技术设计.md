## 1. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 小程序 | 微信小程序**原生**（JS + WXML + WXSS） | 非 TypeScript、非 uni-app；自定义 tabBar |
| 地图 | 高德微信小程序 SDK（`libs/amap-wx.130.js` 本地文件） | 坐标系 **GCJ-02**，全链路不做 WGS-84 转换 |
| 后端 | Node.js ≥ 20 + Express 4（CommonJS） | `asyncHandler` 包裹异步路由，兼容 Express 4 |
| 数据库 | MySQL 8（微信云托管 Serverless MySQL） | utf8mb4；空间数据用 JSON 列，几何计算全在应用层 |
| 定时任务 | node-cron | 轨迹清理、热度重算 |
| 部署 | 微信云托管（容器） | `wx.cloud.callContainer` 调用，微信注入 `X-WX-OPENID` |
| 测试 | node:test + supertest | 测试强制走内存数据源 |

运行时依赖极简：`dotenv / express / morgan / mysql2 / node-cron`。

**几个选型决定**：

- **不用 PostGIS**。距离 / 区域判断在应用层十几行数学就够，且纯函数比 SQL 好测。等真要做「附近路线」这类空间索引查询时再引入，见 §10。
- **空间数据用 JSON 列**。轨迹是几十 KB 的数组，JSON 列足够；清空时直接置 NULL。
- **判定用应用层数学**。`server/src/geo/` 是纯函数、无 IO，重点单测。

## 2. 系统架构

### 2.1 分层

```
微信小程序                     微信云托管
┌──────────────────┐          ┌────────────────────────────────────┐
│ pages/  页面      │          │ routes/      HTTP 层（解析入参、拼响应）│
│ components/ 组件  │  HTTP    │ services/    业务逻辑（不碰 req/res）   │
│ utils/ 请求/地图  │ ───────▶ │ repositories/ 数据访问（唯一碰 SQL 处） │
│   request.js      │ call-    │ geo/         纯几何函数（无 IO）        │
│   mock.js(数据层)  │ Container│ store/       内存实现（本地开发）       │
└──────────────────┘/wx.request│ db/    连接池/迁移/建库                 │
                               │ jobs/  定时任务                        │
                               └────────────────────────────────────┘
                                          │
                                    MySQL 8（云托管）
```

### 2.2 分层铁律

- `routes/` 只做 HTTP，不含业务分支。
- `services/` 不含 `req`/`res`，可被测试与定时任务直接调用。
- `repositories/` 是**唯一接触数据源**的地方；`services` 及以上不感知数据从哪来。
- `geo/` 与 `statsService`/`difficultyService` 是纯函数、无 IO、重点单测。

**这套分层的回报**：数据源从「内存 mock」切到「MySQL」，只新增一套 repo 实现 + `DATA_SOURCE` 开关，`services`/`routes` 零改动。

## 3. 数据源与身份

### 3.1 数据源双实现

`config.dataSource` 二选一，repo 层内部按开关分发：

| 取值 | 场景 | 行为 |
|---|---|---|
| `memory` | 本地开发 / **所有测试** | `store/memoryStore.js`，Map 存数据，重启即重置，启动灌 3 条 mock 路线 |
| `mysql` | 线上（云托管） | `db/pool.js` 连接池 + 各 repo 的 SQL 实现 |

两套实现对外契约完全一致（方法名、返回结构），所有方法统一为 async（内存实现本是同步的，为互换性包成 Promise）。

> **测试环境无条件走内存**：`config.js` 里 `isTest`（`NODE_TEST_CONTEXT` 或 `NODE_ENV=test`）时强制 `memory`。否则本地 `.env` 配成 mysql 后跑测试会连真库并写脏数据。

### 3.2 身份识别

无登录系统。`middleware/userId.js` 按优先级解析 `req.userId`：

1. **`x-wx-openid`** —— 线上。小程序经 `callContainer` 调用时微信网关注入，容器内无法伪造，可信。存为 `wx_<openid>`。
2. **`x-user-id`** —— 本地开发。明文请求头，谁都能改；只在本地生效（线上有 openid 时优先级更高）。这是开发期便利，**不是安全边界**。
3. **固定 `test-user-001`** —— 兜底，保证任何情况都有身份、不 500。

## 4. 数据模型

数据库共 10 张表，迁移文件在 `server/sql/`，启动时幂等执行（跑过的记在 `schema_migrations` 里）。

### 4.1 表清单

| 表 | 迁移 | 作用 |
|---|---|---|
| `routes` | 001 + 002 + 005 | 路线主表，含轨迹、难度、区域、审核状态 |
| `comments` / `road_conditions` | 001 | 评论 / 路况提示 |
| `run_records` | 002 | 跑山成绩（72h 后清轨迹） |
| `favorites` | 002 | 收藏（user × route 唯一） |
| `banners` | 002 | 活动位（人工落库，算法位不落库） |
| `moderators` | 002 | 版主及辖区 |
| `users` | 003 | 昵称 / 头像 base64 |
| `client_errors` | 004 | 客户端错误日志（只写不读） |
| `moderator_applications` | 005 | 版主申请（**已建表，接口未接入**，见 §11） |

### 4.2 routes（核心表）

```
id, name, vehicle_type('car'), distance_meters
start_point / end_point   JSON  {lat, lng, radiusMeters=30}
waypoints                 JSON  [{name, lat, lng}]
reference_track           JSON  全量轨迹 [{lat,lng,altitude}]  ← 难度计算的数据源
display_track             JSON  DP 抽稀后的轨迹（≤100 点）      ← 地图绘制用
uploaded_by               'system' 表示官方 mock
curve_count, sharp_curve_ratio(0~1), elevation_gain_meters
road_width                narrow|medium|wide
difficulty_stars          1~5
province, city            区域（列表筛选 + 版主辖区）
road_type                 mountain|track|gravel|highway
heat                      热度，定时任务重算
pinned                    版主置顶
visibility                public|private
review_status             pending|approved|rejected|deleted
review_reason, reviewed_by, reviewed_at
created_at
```

**为什么同时存全量轨迹和抽稀轨迹**：难度必须用全量算（先抽稀会把连续转向合并，弯道数偏少）；而详情接口返回全量会让响应体膨胀到十几 KB，地图绘制用 100 点的 `displayTrack` 视觉上无差别。

**软删除**：删除路线只把 `review_status` 置 `deleted`，不物理删行——路线下面挂着别人的评论、成绩、收藏，物理删会级联清掉不属于作者的数据。软删后所有查询自动过滤掉。

### 4.3 run_records

```
id, route_id, user_id, vehicle_type
raw_track_points   JSON  原始轨迹，expires_at 到点后置 NULL
status             recording|completed|invalid
score              0~1000，对外
rank_no            插入时算的名次（仅结果页用；榜单查询时现算）
total_time_seconds 内部字段，不对外
created_at, expires_at (created_at + 72h)
```

索引：`(route_id, total_time_seconds)`（算分高频）、`(expires_at)`（清理任务扫）、`(user_id, created_at)`。

### 4.4 ID 与时间

内存实现用自增计数器给 `id`，时间用 `new Date().toISOString()`（ISO 8601 字符串）；MySQL 用 `BIGSERIAL`/`AUTO_INCREMENT` 与 `DATETIME(3)`，repo 层统一转 ISO —— **API 返回的 JSON 结构两套实现保持一致**，小程序端不需要感知。

### 4.5 坐标系

高德 SDK 返回 **GCJ-02**。数据库统一存 GCJ-02，**不做 WGS-84 转换**（当前没有跨源数据）。将来接入 GPS 原始轨迹（WGS-84）时必须先转换——**这是已知的坑，提前标记**。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 存活探针 |

### 5.6 统一错误响应

- 业务错误：`AppError`（含 `code` / `message` / `status`），`errorHandler` 转 `{ error: { code, message } }`。
- 4xx（如 JSON 解析失败）：转 `INVALID_JSON` / `BAD_REQUEST`，不算服务器故障。
- 5xx：兜底「服务器内部错误」并打日志。

## 6. 关键算法实现

全部在 `server/src/geo/` 与 `services/*Service.js`，**纯函数、有单测**。前端 `utils/runGeo.js`、`utils/trackSimplify.js` 有**镜像实现**——跑山时每 2 秒要判断是否到终点，不可能发请求问后端。

> ⚠️ **两侧算法必须保持一致**，否则会出现「前端说到终点了、后端说不匹配」的诡异问题。改一侧时必须同步另一侧。

### 6.1 难度计算（`statsService` + `difficultyService`）

```
1. 距离     Σ haversine(p[i], p[i+1])
2. 转向角   相邻三点 bearing 差，归一化到 (-180, 180]
3. 弯道数   转向角 > 30° 的顶点为「转向点」，连续转向点合并为一个弯道区间，
           区间数即弯道数（中间有一个顶点不到阈值就断开）
4. 急弯占比 弯道区间内峰值角 > 60° 记为急弯，急弯数 / 弯道数
5. 爬升     Σ max(0, alt[i+1] − alt[i])，altitude 缺失按 0
6. 星级     normCurvesPerKm 与 normGainPerKm 各归一化到 [0,1]，取**较大者** × 5 四舍五入，夹到 1~5
```

实现要点（`statsService.countCurves`）：用一个 `inCurve` 状态机扫描顶点，遇超阈值顶点开区间并记录峰值角，遇未超阈值顶点关闭区间并结算；**区间按顶点索引连续合并**，中间有一个不到阈值就断开。

阈值集中在 `constants.js`：`TURN_THRESHOLD_DEG=30`、`SHARP_TURN_DEG=60`、`CURVES_PER_KM_MAX=6`、`GAIN_PER_KM_MAX=100`。

### 6.2 路线重合度（`geo/similarity.js`）

- **不用几何中心**：跑山路线大量是环形，环的重心在山体内部、离路线几公里，比中心会失效。
- **采样点覆盖率**：沿 A 等距采 50 点，逐点算到 B 的最短距离，小于阈值（**50m**）算命中；A→B 与 B→A 各算一次，**取较小值**。取 min 而非平均，处理「短路线套在长路线里」——2km 的一段恰好是一条 20km 路线的一部分时，取 min 明确判为「不是同一条」。
- **按距离采样而非按下标**：GPS 点间距不均匀（开快时稀疏、堵车时密集），按下标会让慢速路段获得过高权重。
- **阈值来源**：同路双向车道间距 10~30m + 手机定位误差 5~15m，故 50m 能容下正常偏差又不误判相邻山路。
- **复杂度**：O(采样数 × 目标折线点数)。目标折线先用 DP 抽稀（容差取阈值 1/10，几何误差远小于判定阈值）。
- **档位**：`duplicate ≥ 0.85 / similar ≥ 0.6 / partial ≥ 0.3 / distinct`。
- **两步走（性能）**：先用起点 **30km** 半径从库粗筛候选，只对候选精算重合度。粗筛半径 30km——同一条山路的不同入口/走法起点一般不超过这个量级。

### 6.3 跑山算分（`runService`）

```
1. dataMode=local_only → 不落库直接返回
2. 轨迹匹配（matchTrack）得到有效用时 total_time_seconds
3. 查该路线历史有效记录的用时分布，算本次百分位
4. score = 百分位 × 1000（四舍五入）
5. 名次 = 比自己快的人数 + 1
6. 落库（raw_track_points 存全量，expires_at = now + 72h）
```

**轨迹匹配分两种情况**（`matchTrack`）：

- **闭环**（起终点相距 ≤ 起点半径）：不能取「第一次进终点」——那会得到出发瞬间的下一个采样点、用时接近 0。正确做法：找**离起点最远的点**，再找它之后第一次回到起点区域的时刻。同时要求「最远距离 > 起点半径」，否则可能只是原地移动。
- **非闭环**：第一次进起点区域 → 之后第一次进终点区域，取时间差。同样不能简单取首尾点。
- 时间戳兼容秒 / 毫秒（`< 1e12` 视为秒）；时间倒流或为 0 视为匹配失败。

**没有历史成绩时**不给 0 分（用户会以为系统坏了），给跟路线难度挂钩的保底分：1 星 500 分起步、每星 +50。

**名次查询时现算**：`rank_no` 是插入当时算的，后续有更快的成绩插进来就失真。名次本质是「排序后的位置」，榜单接口按用时排序取行号，`rank_no` 只用于「刚跑完」的结果页。

### 6.4 轨迹抽稀（`geo/simplify.js`）

- **Douglas-Peucker**（保形状）：用于 `displayTrack`（地图绘制）与重合度比对的参照折线。用**显式栈**代替递归（轨迹可能上千点，避免爆栈）。
- **转向角法**（`utils/trackSimplify.js`，保留弯道）：用于生成高德导航 URL——导航只需要关键转弯点，直线段插点无意义。最小间距取**总长的 1/40**（固定米数不行：紧凑盘山路会被过滤得只剩首尾）。
- `simplifyToMaxPoints` 用**二分容差**逼近目标点数，比「先全量抽再截断」好（后者会丢尾部整段）。

### 6.5 导航与分享（`utils/amapShare.js`）

走**复制高德链接到剪贴板**（`m.amap.com/navigation/carmap` 链接），能带上起终点和全部途经点。链接格式来自高德 App 实测分享结果：

- `viaaddr` 是**按字段分组**而非按点分组：`经度组,纬度组,名称组`，组内 `|` 分隔、组间 `,` 分隔，三组元素个数必须一致。
- 不用 `__r=` 那段旧格式（位置敏感、含分享令牌）。

**试过但不可行的方案**（别再走一遍）：

- `MapContext.openMapApp` —— 参数只有一个点，**没有途经点**。
- `wx.navigateToMiniProgram` 跳高德小程序 —— 高德没有独立地图小程序。
- `web-view` 打开 amap.com —— 微信不允许把高德域名配成业务站点域名。

**闭环路线**（起点=终点）走外部导航无意义，页面会提示；导航 URL 生成时截掉后半程、把最远点当终点。

## 7. 小程序端技术

### 7.1 工具层（`utils/`）

| 文件 | 职责 |
|---|---|
| `request.js` | 请求封装：本地 `wx.request` / 云端 `callContainer` 二选一；超时 15s、**网络失败重试 2 次**（简单退避）；错误分流（人话给用户、细节给上报）；GET 参数自行拼 URL（`callContainer` 不会自动转 query） |
| `env.js` | 环境判定：**开发版走本地直连、体验版/正式版走云托管**（`wx.getAccountInfoSync` 的 `envVersion`） |
| `mock.js` | 数据访问层（名字叫 mock，实为 API 调用聚合），页面只依赖它的函数签名 |
| `errorReporter.js` | 错误上报（见 §8） |
| `amap.js` / `amapShare.js` | 高德 SDK 初始化与分享链接构造 |
| `location.js` | 定位权限：拒绝后引导 `openSetting`；**失败一律 resolve，不阻塞浏览** |
| `runGeo.js` / `trackSimplify.js` | 与后端 `geo/` 对应的前端镜像算法 |
| `format.js` / `user.js` / `roadWidth.js` / `placeHistory.js` / `navigation.js` | 格式化、展示名、路宽枚举、地点搜索历史、分享 |

**为什么 `request.js` 要自己拼 GET query**：`wx.request` 会自动把 `data` 转成 query，但 `wx.cloud.callContainer` 会把 `data` 当请求体。为两种模式行为一致，统一自己拼。

**为什么 `env.js` 不写死地址**：本地调试需要「改完代码立刻生效」，部署体验版需要「能上真机」。两个场景要的东西相反，写死任何一个都会让另一个变难用。开发版 → 本地直连（模拟器 `localhost`、真机局域网 IP）；体验/正式版 → 云托管。

### 7.2 自定义 tabBar 的坑

`custom-tab-bar` 渲染在 `page` 标签之外，**拿不到 `app.wxss` 里定义在 `page` 选择器下的 CSS 变量**。因此它的颜色全部写死常量，改配色时须与 `styles/tokens.wxss` 手动同步。详见 [产品设计/01-全局框架.md §3](./产品设计/01-全局框架.md)。

## 8. 错误处理与可观测性

**原则：技术细节永远不给用户看。**

| 谁看 | 看什么 | 在哪 |
|---|---|---|
| 用户 | 一句白话（「网络开小差了，请稍后再试」） | `wx.showToast` / 页面错误态 |
| 管理员 | 完整细节：URL、错误码、errMsg、页面、机型、版本 | `client_errors` 表 |

- **前端**：`errorReporter.js` 收集（自动带当前页面路径、机型、SDK 版本），静默 POST 到 `/api/client-errors`；断网时进本地队列（上限 20 条，存 Storage），下次补发。云端模式下没有可用绝对地址，由 `request.js` 借已建立的通道捎带（`flushWith`），避免循环依赖。
- **后端**：`/api/client-errors` 全字段截断（不让客户端决定写多大），单次批量上限 20 条，写入失败只打日志不影响响应。
- **查询**：
  ```sql
  SELECT created_at, code, message, page, url, model, system
    FROM client_errors ORDER BY id DESC LIMIT 50;
  ```
- **改代码时注意**：`.catch(err => showToast(err.message))` 这种写法要改成「展示固定白话 + `reporter.report({ detail: err.detail })`」。

### 健壮性设计（`index.js`）

- **启动不因数据库挂掉而退出**：库连不上时服务照常监听，`health/ready` 报 not-ready，等库恢复后重启或再调即完成初始化。比崩溃重启好——后者会陷入 Back-off、日志刷屏且永远进不去。
- **数据库初始化必须自动化**：MySQL 模式下启动时自动「建库 + 建表 + 灌示例」，全幂等。因为库不存在时容器起不来、进不了 WebShell，手动迁移会成死循环。
- **端口监听失败显式处理**：把 `EACCES / EADDRINUSE / EADDRNOTAVAIL` 翻译成人话，避免裸的 "Unhandled 'error' event"。
- **优雅退出**：SIGTERM/SIGINT 时关连接池，10 秒兜底强退。
- **`asyncHandler`**：Express 4 不捕获 async 抛错，不包的话请求会挂起不返回、服务端连日志都没有。

## 9. 定时任务

| 任务 | 时间 | 动作 |
|---|---|---|
| 轨迹清理 `cleanupTracks` | 每小时第 **7** 分钟 | `expires_at < now` 的记录 `raw_track_points` 置 NULL，**score/rank 保留** |
| 热度重算 `recomputeHeat` | 每小时第 **37** 分钟 | 按最近 30 天的跑山(×10)/收藏(×3)/评论(×2) 重算 `routes.heat` |

两个任务错开，都要扫表，撞一起会互相拖慢。

**热度为什么定时重算而不是实时累加**：列表页刷一次就写一次库，且用户狂点刷新就能把自己刷上榜首。热度是推荐排序用的**派生指标**，延迟一小时无人察觉，换来可随时调权重、可重来。时间衰减（只算近 30 天）防止三年前火过的路线永远压在榜首。SQL 用三个独立子查询再 LEFT JOIN——在一个子查询里 JOIN 三张表会变成笛卡尔积。

**算法位不落库**：首页的「本周最热 / 新路线 / 高难度」在**查询时动态算**（`bannerService.buildAlgorithmicBanners`）。它每天在变，落库就要写定时任务重算还会攒垃圾。人工活动（platform / moderator）才落 `banners` 表。

## 10. 部署

```
微信小程序 ──(体验版/正式版)──▶ wx.cloud.callContainer
                                   │  微信网关注入 X-WX-OPENID
                                   ▼
                          微信云托管（容器）
                          ├─ 镜像：server/Dockerfile（node:20-alpine，非 root，:3000）
                          ├─ 健康检查：/api/health
                          └─ Serverless MySQL 8（内网注入 MYSQL_ADDRESS/USERNAME/PASSWORD）
```

- **不需要**域名、备案、HTTPS 证书。
- 容器以**非 root** 运行；端口用 3000（1024 以下需 root，切非 root 后会 EACCES）。
- 数据库连接信息**不是自动注入业务代码的**，需在服务设置里配 `MYSQL_ADDRESS / MYSQL_USERNAME / MYSQL_PASSWORD`；`config.js` 同时兼容 `DB_*` 前缀供本地连公网库。
- 环境变量见 `.env.example`。

### 本地开发

```bash
cd server && npm install
cp .env.example .env    # 不填数据库则用内存模式
npm run dev             # http://localhost:3000
npm test                # 强制内存，不碰真库
```

小程序：微信开发者工具打开 `miniprogram/`，详情 → 本地设置 → 勾选「不校验合法域名、web-view、TLS 版本以及 HTTPS 证书」。

## 11. 已知缺口与技术债

**已有基础但未接通**：

- `moderator_applications` 表与 `moderatorApplicationRepo.js` 已就位，但**没有接入 service / router，前端也无申请入口**——版主目前只能由 `moderators` 表直接指派。
- `utils/user.js` 的 `displayName` 仍保留 openid→「车友 NNNN」的派生逻辑，作为无昵称时的回落。

**技术演进方向**：

- **空间索引**：目前经纬度距离在应用层算，几千条量级足够快。真到几万条做「附近路线」时，再加 `geometry` 列 + 空间索引（那时才是 PostGIS 的用武之地）。
- **头像存 base64**：小程序 `<image>` 只能加载公网 URL，而 `callContainer` 走内网通道加载不了图片，故头像存 base64（客户端压到 132×132，约 7KB）。真到瓶颈再换 URL——只改 `userRepo` 存取，上层不动。
